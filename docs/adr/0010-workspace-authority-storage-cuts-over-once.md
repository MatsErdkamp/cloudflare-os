# Workspace Authority storage cuts over once

- Status: accepted
- Date: 2026-08-07

## Context

Workspace Authority lives in the existing workspace Durable Object. That object already stores Gadgets, Gatekeeper records, Contract records, tombstones, and Gadget-local binding maps. The authority model adds stable domain identities, immutable policy versions, approval and installation history, generation-bound revocation, verification evidence, retryable external effects, and an append-only event projection.

Typed storage supplies collections, singletons, transactions, and unique or non-unique indexes, but it does not supply foreign keys. Existing numeric workpiece IDs are runtime facet locators rather than durable domain identities. A migration may preserve only Contracts already using the sole current executable format and their bindings; removed Contract formats fail closed under ADR 0024. It must not treat legacy display metadata as provider identity or invent approval evidence that never existed.

## Decision

The workspace Durable Object remains the only authority database. Authority records use the existing typed-storage mechanism and all authority writes pass through one narrow storage module. Existing Contract records are extended in place; they are not copied into a competing Contract Instance store. Gadget binding maps are replaced by a canonical binding collection at cutover and thereafter are, at most, an ignored compatibility projection.

### Common representation

- New domain identifiers are canonical lower-case UUIDv4 strings generated by Workspace Authority, persisted before use, never accepted from repository configuration, and never reused. Existing numeric `WorkpieceId` values remain runtime facet locators.
- Every mutable record has `schemaVersion` and `revision`. A writer supplies the expected revision for compare-and-swap. `revision` is not an authority epoch.
- Records that can invalidate derived authority also have a monotonic `generation`. An Account credential replacement, grant revocation, Source replacement, Consumer revocation, permission change, or Binding replacement increments the relevant generation.
- Immutable policy and evidence records use explicit version or epoch numbers. They are never edited in place.
- Times are integer UTC milliseconds for display, expiry, and retry scheduling. They do not establish audit order or identity.
- Composite keys and indexes use a shared length-prefixed UTF-8 encoding, not delimiter concatenation. Index key constructors are part of the storage module.
- References are stable IDs. The storage writer enforces referential and lifecycle invariants inside the same Durable Object transaction because typed storage has no foreign keys.
- Lifecycle-bearing collections retain a terminal tombstone variant under the same stable ID after local authority is gone. Tombstones omit callable capabilities and retain identity, lineage, terminal reason, terminal sequence, and cleanup status. Contract tombstones continue to use the existing `contractTombstones` collection because deleting a facet is already an explicit runtime transition.

### Schema control and audit

`authoritySchema` is a singleton containing the active schema version, minimum writer version, authority mode (`legacy`, `backfilling`, or `active`), workspace authority epoch, migration ID, checkpoint, and cutover digest. The owner can increment the authority epoch to invalidate every minted Authority Session without changing already-committed decisions. An incompatible old binary must refuse authority mutations rather than silently write an older shape.

`authorityEventSequence` is the next workspace-local Authority Event sequence. `authorityEvents` is keyed by sequence and indexed by event family, operation ID, actor principal, and every typed subject reference. An event stores the fixed event envelope, exact typed subjects, before/after generation or revision where applicable, and bounded non-secret details. Events are append-only and are never the source of truth.

`authorityOperations` is keyed by operation ID and has unique indexes for `(actor, idempotencyKey)` and `(kind, externalCorrelationId)` where present. It stores request digest, state, starting and terminal sequences, timestamps, and terminal result or bounded failure. Reusing an idempotency key with another digest fails.

`authorityEffects` is keyed by effect ID and indexed by operation, target record, state, and next-attempt time. It stores effect kind, non-secret input digest/reference, attempt count, retry deadline, last bounded failure, and outcome reference. External calls occur only after a transaction records an intent. A later transaction records success or schedules retry and appends its Authority Event.

### Principals, Accounts, grants, and Sources

`authorityGrants` stores the owner-issued `manageAuthority` permission for a named workspace member: grant ID, member principal, grant generation, grantor, lifecycle, revision, and timestamps. Active member principal is unique. The permission is non-transitive and separate from build/use permissions.

`workspaceAccounts` stores Account ID, Gatekeeper vendor, exact Provider Account Identity, Gatekeeper account capability, capability generation, lifecycle, owner/grant lineage, display snapshot, and Credential Health. Health stores state, report sequence, observed capability generation, reporter identity, observed time, and bounded reason. Active `(vendor, issuer, subject)` is unique. Cleanup stores required action, effect ID, attempts, next retry, and terminal outcome; lifecycle and health never collapse into one field.

`personalSourceGrants` stores grant ID, granting user principal and User Durable Object reference, consent generation, exact Provider Account and Resource identities, derived Source capability, Source type descriptor hash, scope, lifecycle, and revision. The workspace never stores the Personal Account capability or the grant revoker. Active `(user principal, Provider Resource Identity)` is unique.

`sources` stores Source ID; origin (`workspaceAccount`, `personalSourceGrant`, or `legacyGatekeeper`); origin ID and generation; exact Provider Account and Resource identities when known; protocol/vendor; Source capability and capability generation; canonical Source type and schema hash; display snapshot; lifecycle; revision; and remote-cleanup state. Active `(origin ID, Provider Resource Identity)` is unique. Workspace Account and Personal Source Grant generation mismatches make the Source ineligible immediately. A legacy Source has explicitly unknown provider identity and can serve only its preserved Gadget compatibility binding.

### Projects and Consumers

`projects` stores Project ID, stable name, lifecycle, generation, revision, and creation attribution. Active normalized name is unique.

`repositoryClaims` stores claim ID, Project ID, attributed repository locator and optional subdirectory, claimant, observed metadata, lifecycle, and revision. Locator indexes are non-unique because claims are untrusted metadata and cannot select authority.

`environments` stores Environment ID, Project ID, stable normalized name, lifecycle, generation, revision, and attribution. Active `(Project ID, normalized name)` is unique.

`consumers` stores Consumer ID, kind, lifecycle, generation, revision, Project and Environment where required, exact assigned Binding Set version, and kind-specific identity:

- a Gadget stores its existing numeric Gadget ID, uniquely indexed;
- a Development Session stores the authenticated human principal, lease ID, lease generation, issuance and expiry, uniquely indexed by active lease ID;
- a Workload stores its active Workload Registration ID and generation; provider credential subjects and rotation state live in the registration record rather than the Consumer.

Consumer identity, Environment, and exact Binding Set assignment are never inferred from repository, branch, display, or deployment labels.

`developmentSessionGrants` stores Grant ID, named developer principal, exact Project/Environment/Binding Set version, immutable Development Placement Template hash, grant generation, issuing Authority Manager and permission generation, lifecycle, revision, optional expiry, and maximum lease duration. Active `(developer principal, Project, Environment, Binding Set version)` is unique. A grant authorizes repeated short leases and template-materialized placements only inside that immutable envelope; changing any member, Approval, Source, Authority Mode, shared-state selection, or template hash requires another authority decision. Its generation is included in every Development Session and capability check, so revocation invalidates live sessions immediately. A Personal Source Grant remains separate and must name the same developer where personal mode is used.

`developmentPlacementTemplates` is immutable and keyed by `(Development Session Grant ID, Binding Requirement ID/version)`. It stores exact Artifact Approval epoch, Source/origin generations, Authority Mode, verifier policy/identity where required, binding name, shared-state selection, and definition hash. A per-Session Installation Decision may be materialized by the system only from an exact live template and records the template, Grant, original Authority Manager/permission generation, new Session Consumer, and decision sequence. Receipt expiry or any cited generation mismatch blocks materialization rather than changing the template.

`workloadRegistrations` stores Registration ID, Workload Consumer ID, adapter ID/version, normalized issuer, registration generation, lifecycle, revision, deployment trust-profile hash, and current credential subject/generation/fingerprint. It may hold one explicitly prepared next or retiring previous credential with an overlap deadline and provisioning/cleanup effect references. Active `(adapter, issuer, credential subject)` and active Workload are unique. Provider secrets, JWTs, headers, and raw evidence are never stored. Registration suspension invalidates attachments and suspends dependent Bindings; terminal Workload retirement retracts them. Rotation keeps the Workload identity stable, while a changed subject is accepted only through an explicit generation-checked Authority Operation.

`graduationPlans` stores Plan ID, source Gadget ID, source authority-snapshot digest, optional code-snapshot provenance hash, proposed authority-issued Project/Environment/Binding Set IDs, target Consumer/Grant IDs, item-set digest, operation, lifecycle, revision, and configuration/operational status. `graduationItems`, unique by `(Plan ID, source binding name)`, stores the captured source edge/Contract or legacy IDs and digest; proposed Requirement/version; requiredness, binding name, Source, Authority Mode, shared-state selection, Approval and Installation references; equivalence status; blockers; and prepared/activated outcome. Submitted items are immutable; rebasing creates a new Plan revision and invalidates changed decisions.

`graduationLineage` is immutable and keyed by Lineage ID. It records Plan/Item, source Gadget/binding/Contract or legacy tombstone and snapshot digest, target Project/Environment/Binding Set/Requirement, target Consumer/Grant, Resolution, Contract Instance and Binding, relation (`graduatedFrom` or `rollbackTo`), decision/event sequences, and known hashes. Unknown legacy actors, times, provider identities, and evidence remain explicitly absent.

### Binding policy, resolution, and installation

`bindingSetHeads` stores Binding Set ID, owning Environment, latest version, lifecycle, and revision. `bindingSetVersions` is immutable and stores `(Binding Set ID, version)`, definition hash, creator, creation time, and optional predecessor. `bindingRequirements` is an immutable membership collection keyed by `(Binding Set ID, set version, binding name)` and stores Requirement ID/version, required or optional readiness, Authority Mode, exact Artifact Approval epoch, Source-type and identity constraints, verifier policy, and definition hash. A unique index enforces one binding name per set version.

`bindingRequirementHeads` stores Requirement ID, owning Binding Set ID, latest version, lifecycle, and revision. `bindingRequirementVersions` is immutable and stores the full normalized requirement, its hash, creator, and predecessor. Editing a requirement or membership creates a new version and a new Binding Set version; Consumers remain pinned until explicitly reassigned.

`verificationReceipts` is immutable and stores receipt ID, verifier identity and generation, verifier Source ID/generation, exact Provider Resource Identity, check kind/policy hash, result, issued and expiry times, protocol evidence digest, and invalidation sequence if later revoked. Active receipt lookup is indexed by the entire verification tuple, never by display metadata.

`resolutionStates`, uniquely keyed by `(Consumer ID, Requirement ID)`, is the mutable diagnostic head. It stores expected Consumer, Source, grant/account, approval, verifier, and Binding generations; candidate Source IDs; state (`noCandidate`, `ambiguous`, `verificationRequired`, `ready`, `active`, or `suspended`); bounded reason; active resolution ID; revision; and last evaluation sequence. Ambiguity never selects a winner and Authority Modes never fall back.

`bindingResolutions` is immutable. It stores Resolution ID; exact Consumer generation and Binding Set/Requirement versions; Authority Mode; selected Source and origin generations; Verification Receipt when required; Artifact Approval epoch; Installation Decision; Contract Instance ID; Binding ID and expected Binding generation; evaluator policy hash; and creation sequence.

`artifactProposals` stores Proposal ID, Artifact hash, runtime-profile hash, public-types hash,
canonical Review Bundle manifest hash and R2 reference, Review Comparison hash/reference where
present, baseline Artifact and policy hashes, proposal state, proposer, operation, and evidence
publication state. Failed staging and corrupt/missing evidence are explicit states. ADR 0024 removes
the numeric Contract harness selector.

`artifactApprovals` is immutable and keyed by `(Artifact hash, approval epoch)`. It stores decision status, exact proposal and evidence hashes, policy hash, Authority Manager and grant generation, decision sequence, and supersession/revocation. Approval never installs anything.

`installationProposals` stores Proposal ID, exact placement preconditions, selected Source and generations, Approval epoch, target Consumer/Environment/Requirement versions, intended binding name and expected generation, Contract configuration hash, proposer, idempotency key, revision, and lifecycle. `installationDecisions` is immutable and stores Decision ID, proposal digest, decision, manager/grant generation, decision sequence, and denial or expiry reason. `installationAttempts` stores attempt ID, Decision ID, operation, state, expected placement revisions/generations, created Contract Instance or failure, retry lineage, and timestamps.

The existing `contracts` collection is extended with a stable Contract Instance UUID, schema/revision, Source/Approval/Decision/Consumer/Environment/Requirement references, binding name and mode, verification receipt, lifecycle, facet generation, suspension generation/reason, shared-state key, predecessor/replacement/rollback lineage, and cleanup state. Its numeric ID remains the existing facet locator. Active indexes cover Source, Consumer, Requirement, predecessor, and lifecycle so Source suspension or retraction can enumerate every dependent instance. Retraction moves the enriched record to the existing tombstone collection after hooks and staged actions are disabled.

`bindings` becomes the canonical placement collection. It stores Binding ID, Consumer ID, unique binding name, Requirement/version, Contract Instance ID, status, generation, revision, installed sequence, and replacement/rollback lineage. Active `(Consumer ID, binding name)` is unique. Replacement creates a new Contract Instance and uses one compare-and-swap transaction to retire the old Binding generation and publish the new one. Raw Gatekeeper targets are forbidden except for explicitly tagged legacy Gadget compatibility bindings.

### Evidence retention

`evidenceReferences` stores content hash, R2 key, kind, byte length, integrity state, rooted-by Proposal/Approval IDs, publication operation, and garbage-collection release state. Blobs are uploaded and verified first, the canonical Review Bundle manifest is published last, and only then may a local transaction make the Proposal reviewable. Evidence remains rooted for every live Approval epoch and retained audit policy window.

### Transaction boundary

All local mutations call `AuthorityStore.mutate()`. It validates the actor's current grant generation, idempotency digest, expected revisions and Authority Generations, foreign references, immutable hashes, lifecycle preconditions, and unique placement constraints. One Durable Object transaction writes domain state, operation state, indexes, evidence roots, and contiguous Authority Events. No caller may write authority collections directly.

External effects use an intent/outcome protocol: the first transaction records state plus a durable effect intent and event; the external call occurs outside the transaction; the outcome transaction records the result, schedules retry or cleanup, and appends events. Retried operations and alarms use the same idempotency key and generation preconditions.

### Migration and rollback

Migration is resumable and has exactly one canonical side at every phase:

1. In `legacy` mode, existing Gadget, Gatekeeper, Contract, tombstone, and binding records remain canonical. Deployed mutation chokepoints additionally append idempotent migration deltas, but staged authority rows are not served.
2. In `backfilling` mode, bounded transactions scan legacy primary keys from a persisted checkpoint. `legacyIdentityMap`, keyed by legacy kind and ID, persists generated UUIDs so retries recreate byte-identical references. Each staged row records source key, source revision/digest, and migration version. Deltas are replayed until the legacy high-water mark is stable.
3. A cutover transaction verifies row counts, referential invariants, unique binding names, Contract-to-binding cardinality, and a canonical digest. It appends one baseline Authority Event containing the migration version, counts, digest, and an explicit unknown-history marker, then sets mode to `active` and raises the minimum writer version. Staged rows become canonical atomically; old nested binding and obsolete Gatekeeper fields are ignored thereafter.
4. Temporary staging, delta, identity-map, and checkpoints are retained until the rollback window closes, then removed by an idempotent cleanup effect.

Before cutover, rollback discards only staged authority rows and deltas and returns to `legacy`; canonical data was never changed. After cutover there is no destructive down-migration. Authority UI may be feature-disabled, but old binaries must refuse mutations. Recovery is a forward migration from the active records.

Backfill maps every Gadget to a Gadget Consumer. Every Gatekeeper becomes an identity-unverified legacy Source; its vendor, creation specification, resource URL, and title remain attributed display/provenance only. It does not become a Personal Source Grant and no Provider Account or Resource Identity is fabricated. Existing raw Gadget-to-Gatekeeper edges become tagged legacy compatibility bindings.

Every current-format live or tombstoned Contract receives its own imported Artifact Approval epoch and Installation Decision, even when artifacts match. Missing Review Bundle, Review Comparison, baseline, policy, proposal, or approver provenance is represented explicitly and can never satisfy a policy that requires it. A known `approvedBy` value remains opaque attribution. An unbound current Contract remains explicitly unbound; migration never invents placement. Removed-format records are retired or reset before cutover and are never reinterpreted. Existing Action Log and chat history are not rewritten as Authority Events.

## Consequences

Authority state has one transactional owner, exact revocation epochs, durable external recovery, and queryable dependent indexes. Audit facts cannot get ahead of state, and preserved current-format records remain usable without being promoted into evidence or identity they never possessed.

The schema is larger and all writes must use the storage module. Cutover requires shadow staging and delta capture, but that complexity is temporary and avoids permanent dual-write or dual-read behavior. Rollback after cutover is intentionally forward-only because restoring legacy nested bindings would lose authority history and generation semantics.

## Extended Authority amendment (ADR 0023)

The instruction to extend the existing `contracts` collection in place is superseded. Expand adds
canonical Artifact Approval, Installation Decision, Task Dispatch Decision, discriminated Binding
Resolution, Contract Instance, Binding, Runtime Approval, Template/task/environment/Ratchet, event,
and Effect records without adding task authority fields to legacy `ContractRecord`. Contract Instance
and Binding remain separate. Any duplicated binding name, mode, placement, or task field on legacy
records is a compatibility projection, never another authoritative read/write model. Agent Task is the
task-scoped Consumer discriminator and has no Environment Binding Set. The one atomic cutover makes
the new collections sole authority and Gadget maps become projections.
