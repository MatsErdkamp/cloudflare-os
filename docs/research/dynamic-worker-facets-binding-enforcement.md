# Dynamic Worker Facets semantics relevant to Binding enforcement

**Research date:** 2026-08-09  
**Scope:** Cloudflare Dynamic Worker Facets (`ctx.facets`), Workers RPC, Durable Object lifecycle, and the installed first-party Cap'n Web 0.8.0 package. This note distinguishes documented guarantees from behavior that issue #22 must prove experimentally. It does not treat current repository workarounds as platform guarantees.

## Executive conclusion

Facets give the supervisor a useful hard boundary: every facet has a SQLite database isolated from the supervisor and other facets, while the supervisor alone chooses when and with which class a named facet starts. The public contract says `abort(name, reason)` synchronously shuts down the running facet, preserves storage, and invalidates all existing stubs to that facet; `delete(name)` also aborts and permanently deletes that facet database. A later `get()` creates/resumes the named facet and can load a different class.

Those documented facts are not sufficient by themselves to prove fail-closed Binding revocation. The current primary documentation does **not** say whether "all existing stubs" includes every callback, derived `RpcTarget`, forwarded/proxied stub, iterator, or stream obtained through the facet; what happens to in-flight calls and transferred streams; whether an existing facet stub survives ordinary hibernation/restart; whether supervisor and facet lifecycles are coupled; or whether `abort()`/`delete()` is ordered atomically with supervisor storage. More seriously, current `workerd` source makes `get()` lazy and appears to let a never-used, pre-abort `Fetcher` materialize the old startup callback after `abort()` because no named actor container existed to invalidate. These are security-relevant unknowns and should remain explicit prototype cases.

A canonical Binding generation stored only in supervisor storage cannot be synchronously read by facet code: the databases are mutually inaccessible, and Workers RPC calls are always asynchronous. Enforcement therefore needs either a facet-local generation snapshot or an injected immutable value/capability, plus an acknowledgement protocol; it cannot rely on a synchronous cross-database read or a shared transaction.

## Local first-party package and runtime-type observations

The workspace installs `capnweb` **0.8.0**. Its README is available at [`packages/workshop-shared/node_modules/capnweb/README.md`](../../packages/workshop-shared/node_modules/capnweb/README.md) and identifies the upstream repository as [`cloudflare/capnweb`](https://github.com/cloudflare/capnweb/tree/v0.8.0). Relevant package-level facts are:

- `RpcTarget` instances and functions are passed by reference; values received remotely are `RpcStub`s.
- A stub may be passed over another independent RPC connection, presently with calls proxied through the introducer.
- On Workers, Cap'n Web aliases the native `RpcTarget`; native RPC stubs/promises can cross Cap'n Web and vice versa, and Workers Service Bindings and Durable Object stubs are supported through proxying.
- Session loss breaks associated stubs; `onRpcBroken()` observes a broken connection or rejected promise.
- Callers own returned stubs and must dispose them. Session end disposes all session stubs. Disposal of an `RpcPromise` may cancel it, but cancellation is not guaranteed.

The generated first-party Workers types at [`packages/workshop-backend/worker-configuration.d.ts`](../../packages/workshop-backend/worker-configuration.d.ts) currently declare:

```ts
interface DurableObjectFacets {
  get<T extends Rpc.DurableObjectBranded | undefined = undefined>(
    name: string,
    getStartupOptions: () =>
      FacetStartupOptions<T> | Promise<FacetStartupOptions<T>>,
  ): Fetcher<T>;
  abort(name: string, reason: any): void;
  delete(name: string): void;
  clone(src: string, dst: string): void;
}
```

`clone()` appears in generated types but is absent from the current public Facets reference. It should not be used for an authority mechanism without separate first-party documentation and prototype coverage.

The current Workshop implementation at [`packages/workshop-backend/src/overseer.ts`](../../packages/workshop-backend/src/overseer.ts) explicitly says facet stubs currently cannot be sent over RPC and wraps one in a `Proxy` plus native `RpcStub`. This is useful evidence of the deployed integration's present limitation, but it is not itself a Cloudflare API contract and may become stale.

The current open-source runtime inspection in this note is pinned to [`cloudflare/workerd@19b1657bd4d53381011b105641e25f1e2da93fd5`](https://github.com/cloudflare/workerd/tree/19b1657bd4d53381011b105641e25f1e2da93fd5). Source behavior is stronger diagnostic evidence than an inference from generic API docs, but only the published API contract should be treated as stable; source-only behavior and doc/source tensions still require a production-runtime conformance test.

## Security conclusions for Binding enforcement

1. **Supervisor storage remains canonical.** Facet storage isolation is a security benefit, but it prevents a facet from synchronously consulting the canonical supervisor record.
2. **Generation must be checked at every release/invocation boundary.** Abort invalidation is a useful coarse kill switch for materialized facet actor channels, not proof of revocation for unused lazy `Fetcher`s, derived capabilities, callbacks, streams, or iterators.
3. **Activation needs acknowledgement.** Because the startup callback is conditional and cross-boundary calls are asynchronous, protected results should not be exposed until the particular facet/enforcement endpoint acknowledges the exact supervisor-owned Binding generation.
4. **Use durable tombstones/generations, not in-memory flags.** Both normal hibernation and unexpected restart discard memory, and there are no shutdown hooks.
5. **Do not claim atomic revocation across databases.** Supervisor writes and facet `abort()`/`delete()` are separate operations with no documented shared transaction. Use an ordering that fails closed after a crash, then reconcile idempotently.
6. **Do not persist forwarded proxy capabilities as durable authority.** Native forwarding is execution-context-bound, and Cap'n Web proxying still depends on the introducer/session. Durable records should identify reconstructible authority, not store an assumption that an old live stub will remain valid.

## Required prototype cases (documentation gaps)

The following should be tested against the production Cloudflare runtime, not only local `wrangler dev`/Miniflare:

1. Materialize a direct facet stub with a successful call, call `abort(reason)`, and prove old calls fail with exactly that reason while a fresh `get()` succeeds against preserved storage.
2. Repeat for `delete()`: prove old direct stubs fail and a fresh same-name facet has empty storage.
3. Before abort/delete, obtain from the facet: (a) an `RpcTarget`, (b) a function callback, (c) duplicated and forwarded stubs, (d) an async iterator/iterator-like target, (e) a readable stream, and (f) a writable stream. Invoke/use each after revocation.
4. Abort/delete during: an in-flight method before storage access, after storage access, a pipelined call, stream backpressure, callback execution, and parallel calls. Verify no protected result crosses the membrane after the revocation commit point.
5. Separately force short-idle actor eviction, full no-client container cleanup, process restart, facet restart, and supervisor restart where possible. Test both an old materialized facet stub and a fresh `get()`, and record whether the constructor and JavaScript startup callback each rerun.
6. Crash/restart between each supervisor generation/tombstone write, facet-local acknowledgement write, `abort()`, `delete()`, and fresh `get()`. Prove every partial ordering fails closed and reconciles.
7. Attempt to return the raw facet `Fetcher` through native Workers RPC and through Cap'n Web 0.8.0, and confirm the documented-source expectation that both reject it as non-serializable. Keep the supervisor-owned proxy membrane.
8. Measure/trace whether direct supervisor-to-facet calls and wrapped/forwarded calls create observably different RPC events, errors, latency, execution-context lifetimes, or billing. Performance observations must not be promoted into correctness guarantees.
9. Exercise the lazy stale-`Fetcher` sequence exactly: `old = facets.get(name, oldClass); facets.abort(name, reason); await old.method()` without any pre-abort use. If old code starts, repeat around `delete()` and require a separate supervisor-owned generation membrane before considering abort/delete fail-closed.
